SECTION 02

핵심 발견 3가지

연구를 관통하는 결정적 사실들. 이 세 가지가 전체 설계의 뼈대다.

① Orca 훅은 이미 "결정 JSON"을 반환하는 구조다

Orca의 PreToolUse 훅은 표준 출력으로 {"decision":"allow"|"ask"|"deny"} 형태의 결정을 반환할 수 있다(antigravity 훅이 공식 시연). 즉 하네스마다 따로 손볼 필요 없이, Orca 훅 한 곳에 Jev 게이트를 넣으면 12개 하네스 전체에 동일한 결정 레이어가 깔린다. 판단 기록은 기존 spool 구조에 자동 적재되므로 그대로 검증 데이터가 된다.

② pi 하네스에는 공식 확장 pi-jev가 이미 존재한다

@alexlikevibe/pi-jev가 pi coding agent의 컨텍스트 압축, 모델 라우팅, /jev 설정 메뉴를 전부 제공한다. 설치 즉시 동작하는 최중요 레퍼런스 구현이다 (SECTION 04).

③ Orca 스킬 공유가 원격 배포의 공식 통로다

Orca는 스킬 번들을 불투명 링크로 게시하면 버전 고정, 롤백, 대상 머신 선택(로컬/paired runtimes/SSH hosts)을 공식 계약으로 보장한다. 수신 머신이 자기 홈 경로를 스스로 해석하므로 머신 간 경로 불일치가 발생하지 않는다. 다른 컴퓨터의 Orca로의 배포는 이 통로가 정답이다.

하네스를 3유형으로 나누면 통합 방식이 명확해진다. 아래 패키지명과 수치는 노트북 지식창고 소스의 기록이며, 적용 시 각 프로젝트의 커밋 고정 링크로 2차 검증을 권장한다.

코딩 CLI
(Claude Code, Codex, Gemini, OpenCode, pi)

SECTION 05

하네스 무관 공통 필수 원칙 3가지

어떤 하네스에 붙이든 이 3가지를 어기면 Jev 연동은 실패한다. 모든 셋업의 검증 기준이다.

① 닫힌 스키마

Jev는 Noul(확률)·Choice(최대 255 옵션)·Score(루브릭)로만 응답한다. 산술·날짜 비교는 못 하므로 결정론적 코드가 사전 계산해 State로 넘긴다. Choice에는 반드시 other/needs_review 예외 옵션을 둔다.

② 중립적 후보 프레젠테이션

State에는 관측 사실만 담는다. "이건 안전함" 같은 결론형 문구가 들어가면 Jev 판단이 흔들린다(자기확증 편향·프롬프트 주입). 유저 입력과 툴 로그는 중립화 후 전달.

③ 신뢰도 게이트 + 페일세이프

p ≥ 0.85~0.90이면 자동 실행, 중간 밴드(0.5~0.85)는 사람 승인(ASK) 또는 상위 LLM 에스컬레이션. 장애 시 가드레일은 Fail-Closed(차단), 라우팅은 Fail-Open(기존 동작)으로 폴백.

SECTION 06

다른 컴퓨터의 Orca로 배포하기

현지 머신에서 완성한 Jev 워크플로우는 3가지 채널로 원격 Orca에 배포할 수 있다. Orca의 공식 문서와 로컬 실측에 근거한 비교다.

채널방식장점판정
A. Orca 스킬 공유스킬 번들을 불투명 링크로 게시, 원격에서 Install from link버전 고정(immutable) + 히스토리 롤백 + 대상 머신 선택(로컬/paired/SSH) 공식 보장, 머신별 경로 자기 해석권장 (주 채널)
B. SSH + 설정 직접 배포agent-hooks 사용자 훅과 설정 파일을 SSH로 배치세밀한 제어, 훅(결정점) 배포에 필수보조 (A와 병용)
C. Orca Web 원격 조작6768 포트 웹 UI로 원격 Orca 접속, 수동 적용즉시 가능, 초기 확인용긴급·예외용
배포 패키지 설계 (Jev 워크플로우 v1). 스킬 4종(jev-gate 게이트, jev-compaction/jev-routing, jev-doctor 진단, jev-smoke 테스트) + agent-hooks 사용자 훅 2종(PreToolUse 결정 병합, Stop 턴 요약) + 머신별 오버라이드용 설정 매니페스트(JSON)로 구성한다. 스킬=지식, 훅=결정점으로 역할을 나눠 배포한다.
보안 메모. Orca Web(6768)이 전면 바인딩(0.0.0.0) 상태다. 원격 접속에 쓰이지만 방화벽 정리와 relay 사용 여부 결정이 배포 전 과제다. orcad 자체는 기본 127.0.0.1 바인딩을 유지하는 것이 안전하다.
SECTION 07

실행 전 다각도 검증: L1~L4 게이트

"다른 컴퓨터에 최적화되어 들어가는지"를 보장하는 4겹의 관문. 하나라도 FAIL이면 다음 단계로 진행하지 않는다.

L1 환경 프리플이트 (jev-doctor)

대상 머신 자동 점검: OS·아키텍처, 하네스 CLI 버전, TYPESAFE_API_KEY 도달성과 지연시간, Ollama 상태, 디스크, 훅 디렉토리 쓰기 권한, quarantine 속성(샌드박스 환경 특유), 훅 백업 존재.

L2 결정 품질 캘리브레이션 (shadow)

Jev 게이트를 3~7일 기록 전용으로 운영: 실행은 기존대로, 판단만 적재. 사람 승인과의 일치율, 오탐·미탐 샘플로 임계값(high 0.85~0.90, keepThreshold 등)을 튜닝. 오분류 데이터는 Jev 노트북에 재적재해 패턴 연구.

L3 통합 스모크 (jev-smoke)

하네스별 표준 시나리오 자동 실행: 파괴적 명령은 deny, 평범한 ls는 allow, 애매한 명령은 ask 기대값 검증. 라우팅(cheap/strong 선택)과 원문 보존 압축도 시나리오화.

L4 롤백 준비

스킬 버전 고정 설치(히스토리 즉시 롤백), 훅 원본 .bak 보존(원복 1줄), Fail 모드 테스트: 가드레일은 Fail-Closed, 라우팅은 Fail-Open이 의도대로 작동하는지 확인.

jev-gate 3단 판정 (검증 결과 포함)

2. Jev API 보조Choice 확률 ≥0.9 allow, ≤0.5 deny, 중간 ask (3초 타임아웃, 실패 시 폴백)
3. 기본미적중 허용 (기존 하네스 동작 보존)
